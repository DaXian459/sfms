## 四、本轮发现的缺陷与修复

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 3 个 S7 端点全 `Offline`，`lastError=目标计算机积极拒绝` | `new Plc(cpu, ip, rack, slot)` 端口固定 102，而模拟器/端点配置在 1102/1103 | 改用重载 `Plc(cpu, ip, port, rack, slot)`（`S7.Net.xml` 中已提供，`Plc.Port` 只读无法后置赋值） |
| 2 | 重启 API 报 `42P07 relation "alarm_event" already exists` | 建表探测写成 `to_regclass('public.tags')`，而实际表名是单数 `tag`，永远判定"不存在" | 探测改为 `public.tag`，并把建表逻辑改为优先走 EF 迁移 |
| 3 | 指标 `endpoint.online = 0`（实际 5 个在线） | 读的是 `endpoint.status` 静态配置列，采集过程从不回写 | 新增 `CollectorRuntime.OnlineEndpointCount`，指标改取运行时连接状态 |
| 4 | `GET /api/history/stats` 返回 500 `42P08 could not determine data type of parameter $1` | `DBNull` 参数无法推断类型 | 显式声明 `NpgsqlDbType.Integer` |
| 5 | 调度抖动 40~86 ms（目标 <50） | 主循环"先干活再 `Task.Delay(50)`"，周期 = 50 + 处理耗时；且配置热加载/落库等 DB 操作挤在同一线程 | ①DB 维护任务拆到独立 `MaintenanceLoopAsync`；②等待时间扣除本次已耗时；③`timeBeginPeriod(1)` 把 Windows 定时器粒度从 15.6 ms 提到 1 ms → **实测 1.7~2.1 ms** |
| 6 | `tag_latest` 每 10 s 全量 UPDATE，SQL 日志刷屏 | EF 逐行更新全部点位 | 只写"值/文本/质量变化"的点位，合并为单条 `unnest(...)` 批量 upsert；启动时用已落库快照做基线 |
| 7 | 5 个画面 `PublishedVersionNo=1` 但 `PublishedVersionId` 为空、版本列表为空、回滚无源 | 种子只写了版本号，没建 `ScreenVersion` 行 | 种子为每个画面创建 v1 并回填 `PublishedVersionId` |
| 8 | 登录第 5 次失败仍返回 401，第 6 次才提示锁定 | 触发锁定的那次请求未返回 423 | 触发即返回 423 并带锁定时长 |
| 9 | 发布画面接口拒绝 `{"json": null}` | `ScreenSaveRequest.Json` 非空约束 | 属预期行为（前端始终传 JSON）；验证脚本改为传草稿 JSON |
| 10 | 删除点位后实时快照仍含该点位，`points.goodRate` 出现 100.9% | 实时存储未清理已移除点位 | `IRealtimeStore.Prune()` + 配置热加载后剔除；指标侧再对 `tagTotal` 取小 |
| 11 | 演示口令 `op123`/`ob123` 为 5 位，与"口令至少 6 位"策略冲突 | 种子数据与校验策略不一致 | 统一改为 `op1234` / `ob1234`，同步更新 README 与运行说明 |
| 12 | 浏览器控制台 `favicon.ico 404` | `index.html` 未声明图标 | 新增 `web/public/favicon.svg` 并声明 |

## 五、结论

- FR-01 ~ FR-14 全部功能点均可实际运行并通过端到端验证；
- 采集链路（S7 + Modbus TCP + Modbus RTU over TCP）5 个端点、110 个点位稳定在 100% 成功率、调度抖动 ~2 ms；
- 写值、报警、历史、导入、组态、权限六条业务闭环均已完成正向与反向用例；
- 已知限制见 `docs/验收对照表.md` 末节。
